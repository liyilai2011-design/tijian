# 分阶段验收

## 第 1 阶段：基础架构

本阶段只核验前后端启动、连接状态、构建和手动重启。沿用已准备的服务器依赖与配置，不为通过本阶段执行数据库迁移、创建账号、业务录入、备份或服务注册。下方已有业务原型和正式部署的验收项目留待后续阶段。

### 前后端开发启动

1. 在项目根目录启动后端：`.\scripts\start-backend.ps1 -Reload`。
2. 在另一个终端启动前端：`.\scripts\frontend.ps1 -Action Dev`。
3. 打开 `http://127.0.0.1:5173`，确认登录网页正常显示，没有白屏，`/api` 通过前端开发服务器转发到本机后端 8000。
4. 确认开发服务器只监听本机 5173；端口冲突时明确报错，不默默换端口。

### 存活与就绪分开检查

在另一个 PowerShell 终端执行：

```powershell
Invoke-WebRequest -UseBasicParsing 'http://127.0.0.1:8000/api/health'
```

必须返回 HTTP 200，响应 JSON 为 `{"status":"ok"}`。无需登录，也不查询数据库。

`/api/ready` 用于连接与 `users` 表检查：现有数据库就绪时为 200 和 `{"status":"ok"}`，未初始化或连接失败时为 503 和中文说明。503 不应影响 `/api/health` 的 200，也不要求本阶段初始化数据库。它不能代替完整业务表、迁移版本和业务流程验收。

### 前端显示真实连接状态

1. 首次打开页面显示“正在检查连接…”，取得 HTTP 200 且 `status` 为 `ok` 后显示“服务器已连接”。
2. 停止后端，点击“重新检查”；应显示“服务器连接失败”及“重试连接”按钮，页面仍可显示。
3. 重新启动后端，点击“重试连接”；应恢复“服务器已连接”，不刷新整个页面或清空当前输入。
4. 检查只在首次打开或手动点击时发起，不连续轮询、不自动刷新整页。

这里显示的是后端存活状态。数据库未就绪时，业务请求仍可以报错；不能把“服务器已连接”当作“系统已可投入使用”。

### 构建与重启

1. 在项目根执行 `.\scripts\frontend.ps1 -Action Build`，退出码为 0，并生成 `frontend/dist/index.html` 和静态资源。
2. 停止占用 8000 的开发后端，再运行 `.\scripts\start.ps1`。
3. 打开 `http://127.0.0.1:8000`，确认直接提供构建后的网页，连接状态正常；此方式不需要前端开发服务器常驻。
4. 手动停止、再次运行启动脚本，确认网页和 `/api/health` 恢复；浏览器重新加载可取得本次构建。

记录启动命令、检查响应、构建结果与重启结果。自动开机启动、数据库迁移、业务权限和备份恢复均不计入本阶段完成项。

## 第 2～4 阶段：数据库、登录、角色权限

开始条件：第 1 阶段通过，且每一阶段前一阶段已完成。验收记录和实际测试结果见 [第 2～4 阶段报告](PHASES_2_4.md)。该轮完成第 4 阶段后停止；第 5 阶段随后另行授权，检查范围见下节。

### 数据库及登录

数据库新增、查询、修改、唯一约束、外键、连接释放、失败回滚及重新建立连接后持久性，在独立临时库用真实 Alembic 迁移和自动化测试验证。

1. 用演示管理员正确密码登录，应进入工作台；错误密码应给出统一提示。
2. 刷新网页，应继续显示工作台；退出并确认后应返回登录页。
3. 未登录直接打开 `/api/users`，应返回 401；已撤销的旧 Cookie 不能恢复登录。

### 账号管理和权限

1. 管理员点击“账号管理”，查看四种角色及医生所属科室。按账号或工作人员姓名查询，应由服务器返回当前页；查询不存在的内容应显示空列表。
2. 点击“新建账号”，填写账号、工作人员姓名、独立密码和角色；选“科室医生”时必须选择科室。正确提交后应显示创建成功，刷新列表应仍能找到账号。实际账号密码由操作人员自行填写。
3. 点击一行“编辑权限”，修改显示名并保存；只有服务器保存成功才显示成功提示。当前管理员的角色和启用状态不能在此改变。
4. 在隔离验收账号上变更角色、科室或停用；原登录会话应失效，重新登录按新权限工作；停用后不能登录。历史操作记录保留。
5. 两个管理员页面编辑同一账号：第一个保存后，第二个旧资料保存应返回冲突并保留输入；点击“读取最新资料（保留输入）”，核对服务器最新姓名、角色、科室和状态，再点击“已核对，保留输入继续修改”后才允许重新保存。
6. 测试环境停止服务器后保存：应显示“数据尚未保存”并保留输入。重启后点击“重试连接”，刷新列表核对服务器状态后再提交。
7. 分别登录前台、科室医生、总检医生，应看不到“账号管理”；直接打开 `/api/users` 仍应返回 403。前台不能总检，医生不能跨科录结果，总检医生不能录科室结果或管理账号。

该轮停止条件：任一关键标准失败先修复；全部通过后停在第 4 阶段，再经用户授权进入第 5 阶段。

## 第 5 阶段：受检者管理（已完成）

开始条件：第 1～4 阶段通过，用户已授权继续。本阶段关键验收已通过，用户已确认人工核对完成；实际测试和浏览器结果见 [受检者管理验收记录](PHASE_5.md)。以下保留复验步骤，使用独立演示库和虚构资料。

### 新增、详情、编辑与查询

1. 管理员和登记员打开受检者页面，新建虚构受检者，填写姓名、性别、生日、手机号、身份证号、单位和备注。保存后查看详情，再刷新列表，资料应仍存在；年龄由服务器返回。
2. 只填写必填资料新增，选填项留空，应可以保存。缺姓名或性别等必填内容应明确提示，不显示保存成功。
3. 身份证号仅验证 15/18 位格式，首尾空白去除、末位小写 x 转大写；非法格式拒绝保存。已有未归档档案的同一证件号不能重复登记；不要求证件号与填写的生日、性别一致。
4. 编辑姓名、生日、联系方式、证件号、单位或备注，保存后从详情、列表及重新打开页面核对。只有服务器成功提交后才显示成功。
5. 分别按姓名、手机号、身份证号搜索；请求由服务器筛选，空搜索结果正常显示。清空条件后恢复列表。
6. 数据超过一页时，翻页应向服务器请求当前页，默认每页 20、最多 100；浏览器不一次加载全部受检者。

### 历史、快照与权限

1. 打开已有体检的受检者详情和体检历史，按页显示体检编号、套餐、日期和进度；该历史接口不返回检查结果、总检结论或报告内容。
2. 在测试资料已有体检后编辑受检者档案：现有体检快照和已发布报告中的原资料应保持原样。身份证、单位、备注不出现在体检和报告响应中。
3. 管理员和登记员可以新增、编辑、查看详情及历史。医生、总检医生看不到受检者管理入口；直接请求对应 API 仍应返回 403，匿名请求返回 401。
4. 只有管理员能归档；必须填写原因。已有有效体检时不能归档；没有有效体检的档案归档后从正常列表移除，数据保留，同一证件号可以重新登记。
5. 自动化验证归档、编辑、创建体检并发时使用共同锁，不留下“已归档但新建有效体检”等冲突状态。新增、编辑审计不复制证件号、手机号或备注值；归档理由仅保存在受保护的审计表中。

### 保存失败与多人修改

1. 两个页面编辑同一档案，第一个保存后，第二个旧版本提交应返回冲突，不覆盖已保存资料，并保留当前输入。读取服务器最新资料并核对后才重新保存。
2. 在独立测试环境停止后端后保存，应明确提示数据尚未保存并保留输入，页面不白屏。恢复连接后先核对服务器状态，再重试。
3. 新增请求响应丢失后，使用原请求编号重试只能返回同一档案，不能重复登记；响应中不回显服务器 SQL 或内部异常。
4. 自动化检查数据库或审计提交失败时资料整体回滚，重启服务后已提交资料仍可查询。

完成条件：受检者管理关键检查、前阶段回归、前端构建与本机预览核对全部通过，并记录实际结果。第 5 阶段完成后已停止；用户随后授权开始第 6 阶段。

## 第 6 阶段：体检登记（已完成）

开始条件：第 5 阶段通过且用户已人工核对、授权开始。本阶段只完善体检登记和保存稳定性：创建体检、唯一编号、受检者关联、日期与登记备注、状态显示、分页查询及多次体检历史。使用现有套餐和检查项目。本轮关键标准、自动化回归、构建及本机浏览器验收已通过，实际证据见 [体检登记验收记录](PHASE_6.md)。当前停在第 6 阶段。

### 登记、关联、详情与历史

1. 管理员或登记员打开受检者页面，查找一名虚构受检者，点击“创建体检”，选择现有有效套餐，填写体检日期和选填登记备注，提交。服务器确认保存后，显示体检编号并进入对应体检详情。
2. 仅选择套餐，日期留空且备注不填，也可以提交；保存后的体检日期应是服务器中国日期（UTC+8），备注为 null。填写日期时应使用所填日期，实际登记时间另外保留。没有受检者、无效套餐、非法日期或超过 2000 字符的备注应拒绝，不显示成功。
3. 详情核对受检者、唯一体检编号、体检日期、实际登记时间、套餐及“待检”状态。登记备注仅在管理员、登记员详情中出现；列表、医生、总检医生及报告不返回登记备注。
4. 为同一虚构受检者再登记一次体检，应得到不同编号和独立记录。打开其档案的体检历史，两次记录都应关联此受检者 id；同名受检者的历史不能混入。
5. 体检列表按受检者姓名或体检编号搜索、按状态筛选，由服务器返回当前页；默认每页 20，最多 100。历史超过一页时也按页请求。体检日期应使用 exam_date，不能混用登记时间。
6. 状态保持“待检 / 体检中 / 待总检 / 已完成”的显示约定。登记页不能手工设置状态；本阶段保留已有流程，具体检查及总检工作台在后续阶段分别验收。

### 不确定结果、重复提交与权限

1. 提交后按钮应禁用，不能连续点击生成重复记录。使用同一账号和同一请求编号重复提交完全相同内容，只返回同一体检，数据库中仅有一组体检、套餐项目和一条创建审计。
2. 独立测试环境停止后端后提交，应提示未保存或尚未确认，保留并锁定套餐、日期、备注及原请求编号，页面不白屏。恢复后用原请求重试，服务器确认前始终不提示成功。
3. 自动化检查已提交请求的重放，以及 HTTP 5xx、响应正文损坏、响应正文超时、HTTP 200 缺少有效 id/编号的处理；不确定结果不能当作成功。前端保持原登记并重试，不能换新请求编号创建第二次体检。
4. 默认日期的请求在中国午夜前成功、午夜后重试，仍返回原体检和原日期。使用同一请求编号改变账号、受检者、套餐、备注或明确日期，应返回冲突，不能覆盖旧登记或读取其他账号的登记结果。
5. 未登录创建返回 401；医生、总检医生创建返回 403。有效套餐、受检者未归档、备注权限由后端校验，手工调用 API 不能绕过。

### 数据一致性、升级与持久性

1. 自动化检查编号唯一约束，模拟编号冲突后有界重试；最多尝试 3 次仍失败时明确报错，不留下部分体检、项目或审计。审计或数据库提交失败时应整体回滚，不得错误返回成功。
2. 并发重复请求应最终对应同一体检；并发归档受检者与创建体检不能出现已归档档案仍产生有效新体检。
3. 迁移前备份并验证备份完整性。旧体检按原 created_at 加 8 小时回填日期；升级后原有体检编号、受检者关联、项目、结果及报告快照应保持一致。
4. 重启后端后重新查找本次虚构登记，体检编号、日期、备注和历史仍保留。执行前阶段回归、前端测试与构建，记录实际结果。

完成条件已满足：本阶段关键标准、回归、构建和本机浏览器验收全部通过，并形成实际验收记录。本轮已停在第 6 阶段，等待授权再进入第 7 阶段。

## 第 6 阶段补充：完整前台登记（已完成）

原第 6 阶段的验收记录仍保留。以下新增要求已完成单独验收，实际结果见 [完整前台登记验收](PHASE_6_COMPLETE.md)；用户已授权通过后继续第 7 阶段。

1. 登记页面上半部分为读取身份证和人员资料，下半部分为本次体检日期、类型、备注及可选套餐，点击“确认登记”一次完成。日期默认服务器今天，年龄自动计算。
2. 统一身份证读取接口提供模拟读取和真实设备未接入提示；模拟资料的姓名、号码及地址均明确虚构。重复模拟读取可找回同一人的已保存档案。
3. 手工录入姓名、性别、出生日期、身份证号、民族、地址等资料；可无身份证登记。无证件时先搜索已有档案，选定已有人员后继续新建本次体检，不凭同名自动合并不同人。
4. 有身份证时通过受保护的 POST 请求精确查找，确认登记时服务器再次核对。并发登记相同身份证只产生一份有效人员档案；人员与多次体检分表关联。
5. 旧档案与读卡姓名、性别、生日不一致时提示核对，不静默覆盖；旧档案民族、地址也不被读卡自动覆盖。编辑档案不改写历史体检与报告。
6. 人员和本次体检在同一事务完成；编号自动唯一且可通过服务器配置改变规则。未选套餐也可登记为待检，无项目不能错误完成总检。
7. 网络失败、响应丢失、重复点击和原请求重试不产生重复人员或重复体检，数据库或审计失败不留下半条登记；明确确认服务器保存后才显示成功。
8. 管理员、登记员可登记、精确匹配及读取完整档案，医生、总检医生和匿名用户不能绕过权限。证件、地址、民族不进入普通日志、临床体检或报告响应；非必要页面不显示完整号码。
9. 迁移前备份，迁移后验证原有临床行和报告、外键完整性；重启后本次资料、编号、日期、类型和历史仍保留。原有回归及前端构建通过。

## 第 7 阶段：科室和检查项目（已完成）

开始条件：第 6 阶段完整前台登记验收通过，用户已授权继续。本阶段只管理基础科室与检查项目，套餐管理留在第 8 阶段。下方 11 项标准均已通过，实际测试、页面和原数据核对见 [第 7 阶段验收记录](PHASE_7.md)。

| 核心标准 | 验收要求 |
| --- | --- |
| 新增科室 | 管理员新增后可查询，空名称及重复名称拒绝 |
| 编辑科室 | 保存后名称和版本正确；旧版本不能覆盖新版本 |
| 停用科室 | 保留原行、账号关联和历史；不再用于新体检或新医生分配 |
| 新增检查项目 | 管理员可新增分类、名称、科室、单位、参考范围、结果类型及异常标记能力 |
| 项目关联科室 | 关联有效科室 ID，非法或停用科室不能用于新启用项目 |
| 单位及参考范围 | 保存、查询、编辑一致；不是自动诊断规则 |
| 不同结果类型 | 文本、数字、是/否三类可配置；新体检快照保留创建时类型，结果值由后端校验 |
| 停用不影响历史 | 已创建体检的项目名称、科室名称、单位、范围、类型及结果不随基础项变更；报告快照保持不变 |
| 管理员可管理 | 页面和接口均允许管理员，记录重要操作审计 |
| 普通医生不能修改 | 医生、总检医生、登记员及匿名不能写基础项目，直接 API 同样拒绝 |
| 数据库关系正确 | 科室、项目、套餐和本次体检项目关系通过外键检查；不用硬删除 |

补充稳定性：列表由服务器分页、搜索、筛选；新增原请求重试只生成一条配置记录；不确定保存结果保留草稿；更新冲突必须核对后继续；审计或提交失败整体回滚。并发停用基础配置和新建体检必须串行，不能创建含停用项目的有效新体检，也不能静默删减套餐项目。既有医生仍可处理原科室历史检查。

## 后续阶段：已有业务原型验收

先按 README 初始化一个独立的演示数据库。所有输入都使用虚构测试资料；演示账号密码由初始化时设置。

### 业务闭环

1. 用 frontdesk 登录，登记“测试受检者”，选择套餐创建体检，记录体检编号。
2. 用 doctor_internal 登录，只能看见本科室待检项目，填写结果并保存；刷新后结果仍存在。
3. 用 doctor_lab 登录，完成检验科项目，选择一个项目手动标记异常。
4. 用 reviewer 登录，核对全部结果和异常，填写总检结论并完成总检。
5. 打开报告网页，核对受检者、项目、结果、总检医生和报告版本；浏览器打印预览应有可读的报告。
6. 重新打开体检必须填写原因；修改结果后再次总检产生第二版报告，原始结果修改记录保留。

### 保存和权限

- 两个浏览器打开同一结果，先后修改；第二个旧版本不能覆盖第一个已保存版本。
- 临时断开测试客户端的局域网，再提交结果；应显示未保存/未确认提示并保留输入。恢复网络后先核对服务器状态，再重试。
- 创建体检请求响应丢失后重试，不能生成重复体检。
- 直接调用 API 也不能绕过角色或科室权限；登记员不能读取检查结果内容。
- 未登录、登录过期和没有总检完成时，均不能获取当前报告。
- 受检者列表和待检列表按页返回，搜索由服务器处理。
